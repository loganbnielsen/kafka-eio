# kafka-eio-core — Design Document

## Overview

Internal shared package used by both `kafka-eio-producer` and `kafka-eio-consumer`.
It is installed as `kafka-eio.core` because the higher-level packages depend on it,
but its raw FFI surface is not the supported user API before 1.0. It exists to avoid
duplicating the FFI layer and error types across the two packages.

Contains:
- Raw FFI bindings to librdkafka (`Kafka_raw`)
- Shared error type hierarchy (`Kafka_error`)
- Shared C stubs (`kafka_stubs.c`)

## Why a Separate Package

`kafka-eio-producer` and `kafka-eio-consumer` both need:
- The same `rd_kafka_t` handle type
- The same error codes (librdkafka's error space is shared across producer and consumer)
- The same C stubs

Without a shared core, both packages would duplicate the FFI bindings and error enum.
More importantly, the autogenerated error variant list (scraped from `rdkafka.h`) would
need to be kept in sync across two places.

`kafka-eio-core` solves this. Users should normally install `kafka-eio-producer`,
`kafka-eio-consumer`, or the facade package and let opam pull core transitively.

## Package Structure

```
kafka-eio-core/
  lib/
    kafka_raw.ml              # unsafe FFI bindings — unstable internal surface
    kafka_raw.mli
    kafka_error.ml            # error type hierarchy
    kafka_error.mli
    kafka_security.ml         # transport security (plaintext/SSL/SASL)
    kafka_security.mli
    kafka_consumer_handle.ml  # opaque handle shared with kafka-eio-producer,
    kafka_consumer_handle.mli # so with_transaction can accept a consumer
                               # without depending on kafka-eio-consumer
    kafka_stubs.c              # C glue between OCaml and librdkafka
  scripts/
    gen_errors.sh          # scrapes rdkafka.h and regenerates the variant list
    check_errors_fresh.sh  # fails if the installed header outruns kafka_error.ml
```

## Kafka_raw

Thin, unsafe FFI bindings to librdkafka. Abstract types prevent misuse — handles are
opaque and cannot be constructed or inspected outside this module.

`Kafka_raw` is installed but unstable. Do not rely on source or binary compatibility
for this module before 1.0; use `Kafka_producer`, `Kafka_consumer`, or the `Kafka`
facade for supported application code.

```ocaml
type kafka_handle   (* wraps rd_kafka_t*       *)
type kafka_conf     (* wraps rd_kafka_conf_t*  *)
type kafka_topic    (* wraps rd_kafka_topic_t* *)

type kafka_type = Producer | Consumer

val conf_new  : unit -> kafka_conf
val conf_set  : kafka_conf -> string -> string -> (unit, string) result
val kafka_new : kafka_type -> kafka_conf -> int (* write_fd, -1 for consumers *)
                -> (kafka_handle, string) result

(* topic_new returns Error rather than a possibly-null handle: a null
   topic pointer stored in an earlier version of this API crashed a
   later produce on that topic. topic_destroy must be called on every
   cached topic before destroying the owning handle — librdkafka's own
   documented lifecycle contract requires topic objects to be destroyed
   before the handle, and relying only on the GC finalizer for this
   risks running it after the handle is already gone. *)
val topic_new     : kafka_handle -> string -> (kafka_topic, string) result
val topic_destroy : kafka_topic -> unit

(* value_opt = None sends a Kafka tombstone (a NULL payload) rather than
   a real zero-length value. *)
val produce  : kafka_topic -> int32 -> bytes option -> bytes option -> int64 (* corr id, 0L = fire-and-forget *)
               -> (unit, int) result
val poll     : kafka_handle -> int -> int
val destroy  : kafka_handle -> unit
val err2str  : int -> string

(* Every transactional call returns more than a bare code: librdkafka's
   rd_kafka_error_t reports, per error instance and not derivable from the
   code alone, whether the producer must abort, whether the failure is
   fatal to the whole producer, and whether it is safe to retry. *)
type txn_error = {
  code           : int;
  is_fatal       : bool;
  is_retriable   : bool;
  requires_abort : bool;
}

val init_transactions  : kafka_handle -> int -> (unit, txn_error) result
val begin_transaction  : kafka_handle -> (unit, txn_error) result
val commit_transaction : kafka_handle -> int -> (unit, txn_error) result
val abort_transaction  : kafka_handle -> int -> (unit, txn_error) result

(* offsets are explicit (topic, partition, offset-of-last-processed-message)
   tuples the caller processed inside the transaction — not the consumer's
   current assignment/position, which could include prefetched-but-
   unprocessed messages. *)
val send_offsets_to_transaction
  :  kafka_handle              (* producer *)
  -> kafka_handle              (* consumer, for group metadata *)
  -> (string * int32 * int64) list
  -> int                       (* timeout_ms *)
  -> (unit, txn_error) result
```

See `kafka_raw.mli` for the complete signature list (partition pause/resume,
commit_message vs. commit_all, admin create_topic, the delivery pipe helpers,
consumer_poll's `poll_result` variant, ...) — it is short enough to read
directly rather than duplicate here.

C stubs translate between OCaml's value representation and C conventions — e.g.
converting librdkafka's `char errstr[512]` error pattern into OCaml result types,
and wrapping C pointers in OCaml custom blocks with appropriate finalizers.

### Blocking C calls — release/acquire pattern

Any C stub that may block for a non-trivial duration **must** release the OCaml
domain lock before the blocking call and re-acquire it before touching any OCaml
values. This keeps the GC unblocked and allows Eio to deliver cancellation as soon
as the call returns, without holding the domain thread hostage.

The invariant has three rules:

1. Extract all needed values from OCaml arguments into C locals **before** releasing.
2. Call `caml_release_runtime_system()` immediately before the blocking C call.
3. Call `caml_acquire_runtime_system()` immediately after. All OCaml allocation
   (`caml_alloc`, `caml_copy_string`, etc.) happens only after re-acquiring.

Pattern (mirrors `ocaml_rd_kafka_flush`):

```c
rd_kafka_t *rk = *((rd_kafka_t **)Data_custom_val(handle_v)); /* before release */
int timeout_ms = Int_val(timeout_v);                           /* before release */
caml_release_runtime_system();
rd_kafka_message_t *msg = rd_kafka_consumer_poll(rk, timeout_ms);
caml_acquire_runtime_system();
/* all caml_alloc / caml_copy_string calls here */
```

Stubs that follow this pattern: `ocaml_rd_kafka_flush`, `ocaml_rd_kafka_consumer_close`,
`ocaml_rd_kafka_consumer_poll`.

**Corollary:** do not use `Eio_unix.run_in_systhread` to work around a missing
release/acquire in a C stub. Fix the stub instead. Systhread offloading creates a
split OS thread that Eio cannot safely cancel while the thread is inside a C frame,
leading to races against handle teardown (`rd_kafka_consumer_close` / `rd_kafka_destroy`)
and eventual memory corruption (exit 139).

## Kafka_error

Mirrors the librdkafka error enum (`rd_kafka_resp_err_t`) directly as OCaml variants.
No lossy mapping — every C error code has a corresponding variant. A catch-all handles
any codes not yet mapped (e.g. from newer librdkafka versions).

```ocaml
type t =
  | No_error
  | Offset_out_of_range
  | Unknown_topic_or_part
  | Leader_not_available
  | Not_leader_for_partition
  | Request_timed_out
  | Msg_size_too_large
  | Network_exception
  | Coordinator_load_in_progress
  | Group_authorization_failed
  | Topic_authorization_failed
  | Transactional_id_authorization_failed
  | Transaction_coordinator_fenced
  (* ... every RD_KAFKA_RESP_ERR_* code — see kafka_error.mli for the full,
     authoritative list; it is not duplicated here so this doc can't drift
     from it the way it once did. *)
  | Err_unknown of int  (* unmapped codes — int allows direct lookup in librdkafka docs *)
  | Config_error of string
  (* producer/consumer construction (config validation, rd_kafka_new,
     subscribe) fails with only a message, no response code. *)

(** Map a raw librdkafka error integer to a typed variant *)
val of_int : int -> t

(** Human-readable description; [rd_kafka_err2str] for real codes,
    the carried message for [Config_error]. *)
val to_string : t -> string

(** True for errors where a retry may succeed (e.g. leader election in progress) *)
val is_retryable : t -> bool

(** True for errors that indicate the kafka handle is no longer usable *)
val is_fatal : t -> bool
```

Constructor names follow OCaml convention: only the first word is
capitalized (`Not_leader_for_partition`, not `Not_Leader_For_Partition`).

## Error Code Generation And Drift

The variant list started as a one-time scrape of `rdkafka.h` and is hand-
maintained from there — it does not regenerate automatically, so it can
silently fall behind a newer installed librdkafka. Two scripts guard
against that:

```bash
# Regenerate the variant list (paste the output in, adjusting as needed)
scripts/gen_errors.sh /path/to/rdkafka.h

# Fail if the installed header defines a code with no matching variant
# in kafka_error.ml — run before a release, or wire into CI
scripts/check_errors_fresh.sh /path/to/rdkafka.h
```

## Transaction Semantics — Reference

This section clarifies exactly what the transactional API guarantees so both the
producer and consumer docs can reference it consistently.

### Exactly-Once Producing (Idempotent Producer)

Controlled by producer config alone — no transactions required. librdkafka assigns
sequence numbers to each message and the broker deduplicates retries. A message is
written to the output topic exactly once even if the network fails and the producer
retries.

Enabled automatically when `delivery_mode = Exactly_once` or `At_least_once` in
`Kafka_producer.config`.

### Exactly-Once End-to-End (Consume-Transform-Produce)

Transactions provide atomicity across both a consumer offset commit and a producer
write. This is the only way to achieve exactly-once semantics across a full pipeline.

The guarantee: either the input message offset advances AND the output message is
produced, or neither happens.

This covers the consume-transform-produce pattern:

```
begin_transaction
  read input message(s) from consumer
  produce transformed message(s) to output topic
  send_offsets_to_transaction (topic, partition, offset) for each input
    message actually processed — not the consumer's current assignment or
    position, which can be ahead of what this transaction processed
commit_transaction              ← both the output message(s) and offsets advance atomically
```

If the process crashes at any point before `commit_transaction`, the broker aborts
the transaction. The input message offset does not advance. The output message is
never visible to downstream consumers. The input message is replayed on restart.

### What Transactions Do NOT Cover

- **Consumer-to-database pipelines** — if you consume a message and write to Postgres,
  Redis, S3, or any non-Kafka store, transactions don't help. Exactly-once there
  requires idempotent writes on the database side (e.g. upsert by message offset).
- **Consuming alone** — there is no "exactly-once consuming" concept in isolation.
  Reliable consumption is at-least-once with careful offset management via explicit ack.
- **Producing alone** — idempotent producer handles this without transactions.

## Dependency Graph

```
kafka-eio-core
  ├── kafka-eio-producer  (depends on core)
  └── kafka-eio-consumer  (depends on core)
```

End users install `kafka-eio-producer`, `kafka-eio-consumer`, or both.
`kafka-eio-core` is pulled in transitively and never referenced directly.
